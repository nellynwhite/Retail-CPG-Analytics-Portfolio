ADR-001 Composite date_key to fix non-unique week_id in Dim_Date Resolved
Problem
Dim_Date contained 104 rows — 52 TY weeks and 52 LY weeks. Both years shared the same week_id values (1–52), making the week_id column non-unique. Power BI refused to create a 1:Many relationship from Dim_Date to any fact table, and filter context was breaking across all four facts.
Options considered
Option A: Keep only TY rows in Dim_Date and join LY via DAX.

Option B: Add a composite key combining week_id + fiscal_year_label to make every row unique.

Option C: Separate Dim_Date into two tables (Dim_Date_TY, Dim_Date_LY).
Decision rationale
Chose Option B. Option A would require rewriting all YoY measures using FILTER/ALL instead of the simpler column subtraction pattern. Option C creates model bloat and requires maintaining two relationships per fact. The composite key preserves the single dimension pattern while making all rows uniquely addressable.
Result: Added composite key = week_id & "_" & fiscal_year_label. All four fact table relationships now resolve correctly with 1:Many cardinality. Filter propagation confirmed across all 77 DAX measures.
Lesson learned: When a dimension needs to track multiple years, always check whether the grain of the primary key is still unique after adding the second period. In Scintilla-style data where TY and LY coexist in the same table, this is a predictable failure point.
ADR-002 Store TY and LY as columns, not using DAX time intelligence Intentional
Problem
Walmart's 52-week NRF fiscal calendar makes standard Power BI time intelligence functions (DATEADD, SAMEPERIODLASTYEAR, DATESYTD) unreliable. These functions operate on Gregorian calendar dates, not fiscal week numbers. A Q1 fiscal period starts in February, not January — causing a systematic off-by-several-weeks error in all YoY calculations.
Options considered
Option A: Build a custom fiscal calendar table and override all time intelligence with FILTER/ALL patterns.

Option B: Store both TY and LY values as columns in each fact table, pre-aligned by fiscal week number at data load time.
Decision rationale
Chose Option B. Option A requires custom DAX wrapper functions for every time-period calculation and is prone to off-by-one errors at fiscal year boundaries. Option B mirrors exactly how Walmart Scintilla exports data — the vendor portal already provides TY and LY in the same row. This makes the model's structure match the source system, which reduces cognitive overhead and onboarding time for anyone familiar with Scintilla.
Result: All YoY measures use simple column subtraction (e.g., [Total Sales TY] - [Total Sales LY]). No time intelligence functions are used anywhere in the 77-measure library. Fiscal year filters work via Dim_Date[fiscal_year_label] slicer rather than date hierarchy.
Lesson learned: Always confirm the retailer's fiscal calendar before designing any time-series analytics in Power BI. What works for a standard enterprise calendar (Jan–Dec) breaks entirely for NRF-aligned retailers. The Scintilla column pattern is the safest approach for Walmart-specific analytics.
ADR-003 Import mode over DirectQuery for Power BI performance Trade-off
Problem
Choosing between Import mode (data compressed in-memory) and DirectQuery (live queries to the SQL database) for Power BI. Both are technically viable at this data volume, but have different performance and refresh characteristics.
Options considered
Import mode: All data loaded into Power BI's VertiPaq in-memory engine. Fast renders, offline capable. Stale between scheduled refreshes.

DirectQuery: Every visual interaction fires a live SQL query. Always current. Slower for complex multi-table queries.
Decision rationale
Chose Import mode. At 52,000 total fact rows, the dataset compresses to under 10MB in VertiPaq. Visual render times average under 500ms vs. 2–4 seconds in DirectQuery testing. For a portfolio demonstration with a static synthetic dataset, Import mode is the correct choice. The SQL views are structured to support a DirectQuery migration if the dataset were connected to a live operational database.
Result: Sub-500ms visual render times across all six dashboard pages. Model file size under 10MB. Scheduled refresh capability confirmed via Power BI Service publishing.
Lesson learned: Import vs. DirectQuery is a dataset-size and refresh-frequency decision, not a capability decision. For production Scintilla data at 600 stores × 52 weeks × thousands of SKUs, DirectQuery or Composite Models become necessary. The SQL views are already structured as the semantic layer to support that migration.
ADR-004 CALCULATE with boolean requires = TRUE() syntax Resolved
Problem
Several measures needed to filter on boolean (bit) columns in the fact tables, specifically is_on_promo and in_stock_flag. Initial DAX expressions using CALCULATE with the column name alone returned incorrect results — the filter was not applying as expected.
Root cause
CALCULATE interprets a boolean column reference as a table filter, not a value filter. Without an explicit comparison, the filter context is ambiguous and Power BI does not apply it correctly in all scenarios. Adding = TRUE() forces an explicit value filter that behaves consistently.
Resolution
Wrong: CALCULATE([Total Sales TY], Fact_WeeklySales[is_on_promo])

Correct: CALCULATE([Total Sales TY], Fact_WeeklySales[is_on_promo] = TRUE())

Applied this pattern consistently across all 14 measures that filter on boolean columns.
Result: Promo Sales TY, Non-Promo Sales TY, In-Stock Rate, and 11 related measures all return correct values across all slicer combinations after adding = TRUE() to every boolean filter.
Lesson learned: Never assume DAX infers intent from a boolean column reference inside CALCULATE. Always use explicit comparison operators. This is a common source of silent calculation errors in Power BI models — the measure returns a number, but it may be the wrong number.

Portfolio summary · Project 1 — Retail Sales Drivers
What does this project demonstrate?
Written for a CPG hiring manager or category director — no technical background required
The business problem
Every CPG vendor selling through Walmart needs to answer one question every week: how is my business performing, and why? Walmart's Scintilla vendor portal provides the raw data, but turning that data into a clear, actionable picture — broken down by category, store, promotion type, and time period — requires a specific combination of analytical and business skills.

This project builds exactly that system from scratch: starting with raw data, building the underlying database, writing the logic, and producing a five-page interactive dashboard that a category manager could actually use to run a weekly vendor review.
What was built, step by step
1
Designed the database. Built a structured data model (11 tables) that mirrors how Walmart Scintilla organizes vendor data — by store, item, week, and promotion type.
2
Wrote the business logic in SQL. Created reusable database views that calculate the KPIs a category manager cares about: year-over-year sales change, gross margin, promo lift.
3
Built the Power BI dashboard. Connected the data to Power BI and created 77 calculations covering sales, inventory, promotions, and supply chain — organized into a five-page interactive report.
4
Documented everything. Wrote plain-English guides for every calculation, every data quality check, and every design decision — so anyone on the team could understand and extend the work.
